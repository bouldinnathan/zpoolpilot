# ZpoolPilot (`zpoolpilot`) — Alpha

**0.1.0-alpha.1 · Experimental alpha · No stable release**

ZpoolPilot is experimental software. Loop-backed collection and packaged
services have been exercised in a disposable Proxmox VM; the validation scope
is recorded in [testing.md](docs/testing.md). Boot recovery, physical enclosure
behavior, and the application's storage-changing workflows still require lab
validation before production use. This source is provided for testing and review.

`zpoolpilot` is a safety-focused terminal dashboard and command-line tool for a
local Linux/OpenZFS host. It correlates pools and vdevs with stable disk
identities, records physical bay labels, reports health through text, JSON, and
Prometheus, and performs supported storage changes only through short-lived,
reviewable plans.

The primary target is OpenZFS 2.3+ on Proxmox VE 9. Read-only monitoring has a
best-effort legacy text fallback; storage planning fails closed unless the
safety-critical discovery sources, including the OpenZFS JSON interfaces, are
available.

## Safety model

- A changing `/dev/sdX` name is never enough to authorize a disk operation.
  Plans pin a WWN, NVMe EUI/NGUID, or unique serial fallback together with the
  `/dev/disk/by-id` path, exact capacity, sector geometry, major:minor device
  number, host identity, and pool-topology fingerprints.
- Planning performs fresh, non-waking discovery. Applying a plan rediscovers
  and revalidates the host immediately before every command.
- Immediately before each red command, a live filesystem guard verifies that
  every argv by-id link still names the pinned block device and sysfs whole
  disk with the planned major:minor number.
- Plans expire after at most 15 minutes. Apply reconstructs the allowlisted
  argv from typed intent and rejects an edited command preview. Plan IDs are
  exactly 32 lowercase hexadecimal characters.
- External programs receive argv arrays directly; no shell parses device,
  pool, dataset, or plan data. Noninteractive output capture is bounded; an
  overflowing command fails closed instead of growing memory without limit.
- Green read operations run automatically. Yellow changes show the exact
  command and use `[Y/n]`. Red operations require the exact `yes SERIAL` or
  `yes FINGERPRINT` challenge; pressing Enter is not approval.
- `apply` requires root and a real terminal. There is no unattended
  assume-yes option. A before/after audit is mandatory.
- `--read-only` installs an independent observer command policy. It rejects
  planning, apply, bay/LED changes, and deliberate disk wake-up.
- Boot-critical pools cannot be changed with generic plans. The implemented
  Proxmox replacement is a distinct, more restrictive workflow.
- Safety-critical OpenZFS JSON must be structurally complete. Status, list,
  and property sources must agree exactly on pool names and GUIDs; bootfs/root
  dataset coverage and scan authority cannot silently disappear.
- The actual `/` mount in `/proc/self/mountinfo` is independent boot evidence.
  A ZFS root marks its pool boot-critical even with `bootfs=none` or
  `mountpoint=legacy`; missing or malformed root-mount authority blocks
  planning.
- Unknown, stale, unsupported, sleeping, timed-out, or permission-denied
  telemetry remains visibly unknown; it is never emitted as a healthy zero.

Color reinforces these labels but is never the only signal. Use
`--color=always`, `--color=never`, or `NO_COLOR=1` as needed.
Snapshot, cache, plan, and error strings are stripped of terminal controls and
Unicode direction overrides before terminal rendering; any ANSI color that
remains is generated by the program itself.

## Build and first inspection

The repository has no network-fetched Go dependencies and requires Go 1.23 or
newer:

```sh
make test
make build
./bin/zpoolpilot --version
./bin/zpoolpilot doctor
./bin/zpoolpilot --read-only status --refresh
```

The installed configuration path is `/etc/zpoolpilot/config.toml`. A missing
configuration file uses safe defaults. Unknown sections/keys and duplicate
settings fail loudly. Configured files cannot collide with derived state or
bay-store lock paths.
When running as root, the configuration must be a singly linked, root-owned
regular file that is not group/other-writable. Every directory ancestor in
its path must be root-owned, nonsymlinked, and not group/other-writable.
Configured write paths are confined beneath `/var/lib/zpoolpilot`,
`/run/zpoolpilot`, `/var/log/zpoolpilot`, and `/etc/zpoolpilot` according to their
purpose.

Runtime commands required for full collection are `zpool`, `zfs`, `lsblk`,
`udevadm`, and `smartctl`. SQLite is recommended for the shared snapshot state
cache; an atomic JSON fallback is included. Authoritative manual bay mappings
live separately in root-owned `/etc/zpoolpilot/bays.json`, and mutation audit
records go to the root-owned JSONL log. `sgdisk` and `wipefs` are needed to
prepare disks. The boot-disk workflow additionally needs
`partprobe`, `pveversion`, and `proxmox-boot-tool`. `sg_ses` is optional for
identify LEDs.

## Dashboard and read-only output

Run `zpoolpilot` or `zpoolpilot tui` for the full-screen dashboard. Its eight pages
cover overview, pools/vdevs, drives/bays, dataset settings, ARC/performance,
tasks, actions, and the redacted command trace. The Actions page explains the
CLI workflow; the dashboard itself never mutates storage.

Use the arrow keys or `p`/`n` to change page, `j`/`k` to scroll, `1`-`8` to
jump, `r` to refresh fast read-only data, `?` for help, and `q` to quit. A
line-oriented fallback accepts the same keys followed by Enter when full-screen
terminal control is unavailable.
Fast dashboard refreshes retain cached SMART readings only for matching drive
identities and reevaluate their age. Failed pool/ARC sources are displayed as
unknown instead of numeric zeroes.

For automation:

```sh
zpoolpilot --read-only status --json
zpoolpilot --read-only status --json --refresh
zpoolpilot --read-only inventory list --json
```

`--include-commands` adds redacted observer command traces to status JSON. It
does not expose interactive encryption input or subprocess output.
Cached traces are omitted unless requested by this flag or enabled in
configuration; `--include-commands=false` explicitly omits them.

The complete command families are:

```text
zpoolpilot [tui]
zpoolpilot status [--json] [--refresh] [--include-commands]
zpoolpilot inventory scan|list|mappings|map|verify|unmap|locate
zpoolpilot plan OPERATION
zpoolpilot apply PLAN.json
zpoolpilot monitor collect|serve
zpoolpilot doctor [--json]
```

## Drive inventory and bays

An inventory row includes risk, bay, current devnode, media/transport type,
make/model, serial, capacity, current use, stable ID, by-id path, and
major:minor number:

```sh
sudo zpoolpilot inventory scan
zpoolpilot inventory list
```

Linux `/dev/disk/by-path` names are shown as `inferred` bay labels when
available. They are controller paths, not proof of a chassis label. `map`
saves a tentative manual mapping with `inferred` confidence and no verification
timestamp:

```sh
sudo zpoolpilot inventory map \
  --drive 'wwn:5000c500aabbcc01' --enclosure /dev/sg2 --bay FRONT-03 --slot 2

# After physically checking it, promote the saved/current values to verified:
sudo zpoolpilot inventory verify --drive 'wwn:5000c500aabbcc01'
```

Manual inferred and verified mappings are keyed by stable disk identity and
overlay cached discovery, so the tentative mapping is immediately available to
`verify`. A duplicate bay assignment becomes a critical conflict finding.
Unknown bays are permitted, but the plan displays `UNKNOWN` and still requires
the exact disk challenge.

The authoritative mapping list includes retired or currently absent drives, so
an old key can be copied exactly without reading the JSON file. Retire that
mapping before assigning its physical slot to a replacement drive:

```sh
zpoolpilot inventory mappings
zpoolpilot inventory mappings --json
# Clear any identify LED before deleting the record. This still works if the
# old disk is absent or the physical verification is older than 15 minutes.
sudo zpoolpilot inventory locate --drive 'wwn:5000c500aabbcc02' --state off
sudo zpoolpilot inventory unmap --drive 'wwn:5000c500aabbcc02'
```

`unmap` accepts only an exact stored `wwn:` or `serial:` key; aliases and
devnodes do not resolve. It deliberately does not require the retired drive to
be present. After its yellow confirmation, it atomically removes the mapping
only if the stored bay record is still identical to the one displayed.
Always clear an active identify LED before `unmap`; once its authoritative
record is gone, the tool intentionally has no slot authority for that key.

`map`, `verify`, `unmap`, and `locate` are yellow changes and require root plus
a real terminal. Their authority is the strict, atomically replaced
`/etc/zpoolpilot/bays.json`, not the shared cache database. Bay rows left in an
older `state.db` are ignored rather than migrated; remap and physically verify
each assignment with the commands above. `map`, `verify`, `locate --state on`
use fresh, fast, no-wake safety discovery. `mappings`, `unmap`, and
`locate --state off` instead operate on an exact stored key so recovery still
works after a retired disk is absent. After confirmation, `map` and `verify`
repeat discovery and require the same drive
fingerprint and major:minor; `verify` also re-probes the enclosure before
storing. `unmap` reloads and compare-and-deletes under the store writer lock. A
missing bay file simply means there are no manual mappings; malformed or
untrusted contents produce partial `inventory.bays`/`trust` status instead of
restoring cached mappings. Packaged installation seeds an empty v1 file and
preserves it on reinstall.

For an enclosure with a manually verified label, timestamp, numeric slot, and
direct SES character-device path:

```sh
sudo zpoolpilot inventory locate --drive 'wwn:5000c500aabbcc01' --state on
sudo zpoolpilot inventory locate --drive 'wwn:5000c500aabbcc01' --state off
```

`locate` always refuses inferred mappings and symlinks. The enclosure must
exist as a direct character device at canonical `/dev/sgN` or
`/dev/bsg/H:C:T:L` and be
SCSI enclosure-services type 13. `verify` pins a reliable udev WWN or hardware
serial; both locate states require that enclosure identity to match before
confirmation and immediately before LED dispatch, with an unchanged trusted
mapping between those checks. Turning the LED on additionally requires the
selected drive to be present with a strong stable identity before and after
confirmation, and the physical verification must be no more than 15 minutes
old. Turning the LED off accepts only the exact key shown by `inventory
mappings`, but permits an absent drive and an older verification so an
orphaned indicator can always be cleared safely. Timestamps over one minute
ahead are refused for both states. `map` may omit a slot, but `verify`
requires an explicitly supplied or saved nonnegative slot; explicit `--slot 0`
is valid. Automatic SES slot discovery is not implemented. Physically verify
the bay label and drive serial yourself, and never pull a disk solely because
its identify LED is lit.

## Plan and apply workflow

Supported data-pool operations are:

```text
create-pool       whole-disk single, mirror, raidz1, raidz2, or raidz3
prepare-disk      remove partition-table and eligible inactive filesystem metadata
replace-disk      replace one leaf vdev
attach-mirror     attach one leaf to form or widen a mirror
expand-raidz      add one disk to a top-level RAIDZ vdev (OpenZFS 2.3+)
add-vdev          add one top-level vdev matching the pool's data topology
add-spare         add one or more hot spares
replace-boot-disk guarded Proxmox boot-pool replacement described below
```

These disk/topology operations are red/destructive. First identify the target
from a fresh inventory, create and inspect the JSON plan as an ordinary
operator, and then apply it from a trusted terminal:

```sh
zpoolpilot plan replace-disk \
  --pool tank --vdev 1234567890123456789 \
  --drive 'wwn:5000c500aabbcc03' --out ./replace.plan.json

less ./replace.plan.json
sudo zpoolpilot apply ./replace.plan.json
```

Plans that consume a disk as a new pool member collect SMART in no-wake `all`
mode. A known failed SMART assessment, critical drive health, or critical
drive finding blocks planning and is checked again immediately before every
command. Missing, sleeping, or unsupported SMART remains a prominent warning
instead of being treated as healthy. `prepare-disk` deliberately remains
available for retiring failed media; routine pool maintenance uses the fast
profile.

Replacement and mirror-attach plans also require a nonzero authoritative size
for the selected vdev. RAIDZ expansion requires a nonzero size for every child
and sizes the new-disk check against the smallest child. Apply rediscovers and
rechecks this size authority before dispatch. Each proposed spare must be at
least as large as the pool's largest data leaf; an unknown data-leaf size
blocks both planning and apply.

If a replacement contains only an inactive ordinary filesystem signature,
prepare it in a separate plan first. Mounted filesystems, swap, any LSBLK or
sysfs holder, active ZFS membership, root, and boot use are hard blockers.
Unmounted raw ownership signatures such as `zfs_member`, LVM, MD RAID, LUKS,
Ceph BlueStore, BitLocker, and swap also block because the tool cannot prove
that their external owner is inactive:

```sh
zpoolpilot plan prepare-disk \
  --drive 'wwn:5000c500aabbcc03' --out ./prepare.plan.json
sudo zpoolpilot apply ./prepare.plan.json
```

Create a mirrored pool with conservative defaults:

```sh
zpoolpilot plan create-pool \
  --pool tank --topology mirror \
  --drives 'wwn:5000c500aabbcc04,wwn:5000c500aabbcc05' \
  --dataset-property compression=zstd \
  --out ./create-tank.plan.json
sudo zpoolpilot apply ./create-tank.plan.json
```

`single` and `raidz1`, mixed capacities greater than 1%, and enabled dedup need
`--expert` and remain prominently warned. The `proxmox` create profile sets
`atime=off` and `xattr=sa`; it does not register storage with Proxmox.
`single` accepts exactly one disk.

Native encryption is available at pool creation with `--encrypt=passphrase`
or `--encrypt=keyfile --keyfile=/absolute/path`. Key files must already exist,
be singly linked regular nonsymlink files, contain 1 byte to 1 MiB, and have
mode `0600` or stricter. At privileged apply time, the key and every directory
in its path must be root-owned, with no group/other-writable directory; place
keys under a protected location such as `/etc/zpoolpilot/keys`. Key contents and
prompted passphrases are never placed in argv, state, metrics, or audit output.
Key files default to ZFS `passphrase` format; select `--key-format=raw` or
`--key-format=hex` only when the existing file actually uses that format.

### Routine pool maintenance

Scrub, manual TRIM, and error-counter changes use the same expiring plan/apply
boundary, but are yellow rather than red:

```sh
zpoolpilot plan scrub-start --pool tank --out ./scrub.plan.json
sudo zpoolpilot apply ./scrub.plan.json

zpoolpilot plan scrub-stop --pool tank
zpoolpilot plan trim-start --pool tank
zpoolpilot plan trim-stop --pool tank
zpoolpilot plan clear-errors --pool tank
```

`scrub-start` blocks any active or unknown scan. It also blocks active or
suspended manual TRIM and unknown or uncertain mixed TRIM state;
`scrub-stop` requires a confirmed active scrub. Despite its CLI name,
`trim-stop` maps to
`zpool trim -s` and suspends a consistently active manual TRIM pass; it does
not cancel it.
`trim-start` starts an untrimmed/complete/canceled pass or resumes a consistently
suspended pass. Unknown, mixed, or unsupported TRIM state blocks start, and an
already suspended pass cannot be suspended again. These suspend/resume semantics
follow [OpenZFS `zpool-trim(8)`](https://openzfs.github.io/openzfs-docs/man/master/8/zpool-trim.8.html).
The pool must be `ONLINE` or `DEGRADED`.

Red lifecycle plans block active scans and active/suspended manual TRIM. They
also block unknown scan or TRIM authority; pool creation checks every imported
pool rather than only the disks selected for the new pool.

Maintenance is allowed on a boot pool but warns about latency and availability.
`clear-errors` only clears recorded counters; it does not repair hardware or
restore data. Each generated plan still requires root, a TTY, fresh pool/GUID
revalidation, and `[Y/n]` confirmation during apply.

## Proxmox boot-disk replacement

This workflow is intentionally narrow. It accepts only a Proxmox host detected
by `pveversion`, a boot-critical mirrored pool, a failed/old leaf on persistent
partition 3, exactly one healthy online sibling whole disk, and a clean
same-size-or-larger replacement whole disk. The healthy source needs usable
no-wake SMART data. Plain `grub-install` layouts are not supported.
The source and replacement must have the same logical sector size so cloning
the partition table preserves byte offsets.

Check and understand the boot mode first:

```sh
proxmox-boot-tool status

zpoolpilot plan replace-boot-disk \
  --pool rpool --vdev OLD_VDEV_GUID \
  --source-drive 'wwn:5000c500aabbcc06' \
  --drive 'wwn:5000c500aabbcc07' \
  --boot-mode systemd-boot \
  --out ./replace-boot.plan.json

less ./replace-boot.plan.json
sudo zpoolpilot apply ./replace-boot.plan.json
```

Use `--boot-mode grub` only when the displayed `proxmox-boot-tool status`
reports GRUB. Planning runs that read-only status command and rejects a mixed,
unknown, or mismatched mode.

The applied sequence clones the healthy disk's partition table, assigns new
disk/partition GUIDs, refreshes the kernel partition view, formats and
initializes replacement partition 2 through `proxmox-boot-tool`, and finally
replaces the old ZFS leaf with replacement partition 3. This mirrors the
documented Proxmox replacement procedure; see the
[Proxmox VE Administration Guide](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf).
Before each step, apply revalidates the planned whole disk. After `partprobe`,
a last-mile guard requires the persistent partition-2 and partition-3 links to
resolve to block partitions owned by that exact whole-disk major:minor device,
and detects a link change during validation.

The tool does not repair an already inconsistent ESP configuration, convert
boot modes, wait for resilver completion, test a reboot, or remove the old
physical disk. Monitor `zpool status`, let resilvering finish, verify
`proxmox-boot-tool status`, and arrange a controlled reboot test before calling
the replacement complete.

## Monitoring and Prometheus

Collectors write one atomic cache snapshot. The exporter serves that cache and
never polls a drive during a Prometheus scrape:

```sh
sudo zpoolpilot monitor collect --profile fast --wait
sudo zpoolpilot monitor collect --profile hardware --wait
zpoolpilot --read-only monitor serve
curl http://127.0.0.1:9815/metrics
curl http://127.0.0.1:9815/readyz
```

A persisted `fast` collection skips SMART and retains the previous hardware
values only when stable ID, WWN, serial, and capacity still match. `hardware`
and `all` use an explicit SMART device type. ATA/SATA reads use
`--nocheck standby,2,2`, which stops on sleeping disks and unsupported or
unknown power-state checks. NVMe reads use `--device nvme`. SAS/SCSI, USB
bridges, and unknown transports are skipped by default and remain unknown:
smartctl cannot enforce the same unsupported-power-state stop for SCSI.
Use the explicit interactive `--wake` refresh for those devices when waking
them is acceptable. Device-type autodetection is only used for that authorized
waking refresh. Controller and firmware behavior still require hardware
validation; this policy is not a hardware guarantee. When a persisted
collector finds a sleeping disk, its previous readings and original timestamp
are retained and marked sleeping instead of waking it. Use `--wake` only for a
deliberate interactive deep refresh; it is a yellow action and is unavailable
under `--read-only`.

Drive telemetry receives an unknown finding when it has never been collected
or is older than twice `hardware_interval`. A SMART time more than one minute
ahead produces an unknown finding during collection; a persisted snapshot with
that timestamp, a missing generation time, or a generation time more than one
minute ahead is rejected, so `/readyz` returns 503. The database fallback gets
the same timestamp validation. Both cache forms require the supported
`SnapshotV1` API version, and invalid cache is not carried forward.

A shared collection lock serializes persisted discovery, merge, and writes
across fast, hardware, and inventory collectors. Failed or canceled collection
leaves the previous cache intact; an older apply-result snapshot cannot replace
a newer collector snapshot. Both the
JSON cache and shared state snapshot use safe replacement/transaction
semantics. Neither is the mutation audit; apply writes mandatory before/after
records to `/var/log/zpoolpilot/audit.jsonl`, which is root-owned and not
writable by the monitoring account.

Status JSON and the TUI also expose conservative per-leaf and aggregate manual
TRIM state, support, progress, bytes, error counts, and action time when
OpenZFS reports them. Mixed or incomplete leaf state remains `mixed` or
`unknown` rather than being guessed.

The Prometheus surface includes:

- host/OpenZFS/Proxmox boot-mode labels plus snapshot timestamp, severity,
  partial state, and collection errors;
- pool state, boot-critical flag, size/allocation/free/capacity,
  fragmentation, I/O errors and rates, scrub/resilver/expansion progress, and
  aggregate manual TRIM state/progress/errors;
- recursive vdev identity, class, state, size, allocation, errors, and manual
  TRIM support/state/progress;
- dataset used/available/referenced/logical bytes, compression ratio, and a
  bounded set of property values with inheritance source;
- drive identity and bay labels, capacity/use state, temperature, SMART result
  and timestamp, endurance used, power-on hours, media/reallocated/pending/
  offline-uncorrectable/CRC errors, sleeping, and unsupported state;
- host ARC/L2ARC sizes, hits, misses, and ARC hit ratio; and
- individual findings plus counts by severity.

Dataset `available` and raw pool free space are deliberately separate.
Fragmentation is a ZFS allocator metric, not evidence of physical disk damage.
NVMe `percentage_used` is preferred for SSD wear. ATA wear is accepted only
from an allowlisted, normalized top-level 0-100 attribute: remaining-life
values become `100 - value`, used-life values are used directly, and raw or
disagreeing vendor values remain unknown. Encryption key locations are
intentionally excluded from metric labels.
NVMe wear above 100% remains visible and triggers the configured critical
threshold. Corrected SCSI errors are kept separate from uncorrected media
errors. Interrupted or incomplete telemetry cannot become a fresh healthy
sample.

The default listener is `127.0.0.1:9815`. `/healthz` reports that the HTTP
process is alive; `/readyz` requires a loadable, non-partial snapshot no older
than its configured maximum; `/metrics` returns the cached snapshot. When an
ARC, pool-list, pool-status, or pool-I/O source fails, the exporter retains its
source-error metric but omits the affected numeric samples instead of
publishing unknown values as zero. A successful legacy fallback remains
exportable even though its failed JSON probe is reported separately.
SMART age findings and drive-health labels are recomputed on each scrape, even
when collectors have stopped. `--max-age` must be positive and controls
readiness; SMART freshness continues to use twice `hardware_interval`.

For a central Prometheus server, keep the default loopback listener and use a
host-local collector/reverse proxy, or bind `monitor.listen` to a dedicated
management address and add only the Prometheus source network to the packaged
service's `IPAddressAllow=` policy. The metrics include drive serials and
physical placement, so do not expose the endpoint directly to an untrusted
network; put authentication/TLS at a reverse proxy when the management network
is not fully trusted.

## Packaged privilege split

The package includes two oneshot collectors and an unprivileged exporter:

- the one-minute fast collector runs as `zpoolpilot`;
- the 15-minute, no-wake hardware collector runs briefly as root for portable
  SMART/controller access but still invokes `zpoolpilot --read-only`;
- the exporter runs as `zpoolpilot` with a private device namespace and listens
  on localhost; and
- no resident service can apply plans.

Enable services only after reviewing `/etc/zpoolpilot/config.toml`:

```sh
sudo systemctl enable --now zpoolpilot-collect-fast.timer
sudo systemctl enable --now zpoolpilot-collect-hardware.timer
sudo systemctl enable --now zpoolpilot-exporter.service
```

See [packaging/README.md](packaging/README.md) for staging and service details.

## Exit status

For status and successfully persisted collector snapshots, `0` means healthy,
`1` warning, `2` critical, and `3` unknown/partial. The packaged collector units
treat `1`-`3` as successful health reports. Operational failures remain
failures: `64` invalid usage, `69` collection did not complete, `74` snapshot
persistence failed, `77` an operation was denied, `78` configuration failed,
and `130` signal cancellation. Planner/apply/doctor failures commonly use `2`;
interactive declines and some general command errors use `1`.

## Scope and test boundary

The current milestone is alpha software validation. The development stages
and completed review work are recorded in [docs/development-plan.md](docs/development-plan.md).
The guarded loop-backed suite has run in a disposable Proxmox VM. Boot-recovery
and representative hardware testing remain later planned stages.

Not yet implemented: automatic SES slot discovery, Proxmox storage
registration, remote/multi-host control, alerts, boot-mode conversion, and
dRAID/log/special/cache-vdev lifecycle management. Existing dRAID and auxiliary
vdev classes are displayed but not changed.

Normal tests are fixture-driven, offline, and non-destructive:

```sh
make check
make test-race
```

The repository also contains an opt-in harness guarded for a disposable VM and
temporary loop-backed pools only; it is not part of the normal test result.
The separately recorded VM run does not validate
real hot-swap hardware, HBAs, firmware, or SES numbering. See
[docs/testing.md](docs/testing.md) before running it.
`make check` compiles that suite without executing it, so its code can be
checked before a lab is available.
